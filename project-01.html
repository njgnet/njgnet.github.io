01 / OVERVIEW

프로젝트에서 만든 환경

팀에서 정한 가상 회사는 SIMMIT PAY입니다. 회원가입과 로그인, 계좌 생성, 송금 기능이 있는 금융 웹 서비스를 운영한다는 설정으로 시작했습니다. 본사에는 인사·개발·영업·재무·보안 부서와 서버망을 두었고, 지사에는 인사·영업 부서와 별도 서버망을 구성했습니다. 본사 영업팀 직원이 외부에서 접속하는 재택근무 환경도 포함했습니다.

서버 쪽은 Rocky Linux를 기반으로 WEB, DB, DNS, FTP, LOG 서버를 분리했습니다. 서버 구축 자체는 다른 팀원이 맡았고, 저는 Packet Tracer에서 각 부서와 서버가 연결되는 네트워크를 구성했습니다. 서버가 만들어진 뒤에는 필요한 포트와 접근 대상이 네트워크 정책과 맞는지 함께 확인했습니다.

전체 구성에는 VLAN, OSPF Routing, ACL, VPN, Dynamic NAT가 들어갔습니다. 이 중 VPN과 Dynamic NAT는 팀원과 같이 작업했으며, 제가 주로 맡았다고 보기 어려워 포트폴리오에서는 협업 항목으로 구분했습니다.

SERVICE금융 웹 서비스회원·계좌·송금 기능과 DB 연동
INFRASTRUCTURE분리된 서버 환경WEB · DB · DNS · FTP · LOG
SECURITY다계층 접근 통제VLAN · ACL · VPN · 방화벽
제가 중점적으로 한 일

전체 토폴로지를 만들고 VLAN과 Routing 설정에 참여했습니다. 그중 제가 확실하게 설명할 수 있는 부분은 ACL입니다. 본사와 지사의 접근 기준을 정리하고 장비에 직접 적용했습니다. 한 규칙을 바꿀 때마다 허용되어야 하는 통신과 막혀야 하는 통신을 다시 확인했고, 마지막에는 본사와 지사 시연 영상도 직접 만들었습니다.

02 / PROCESS

계획부터 최종 검증까지

  1. 01
    계획서 작성·제출

    약 이틀 동안 프로젝트 범위와 네트워크 구성을 정리해 제출하고 강사 피드백을 반영했습니다.

  2. 02
    네트워크 구현

    부서별 VLAN, 주소 체계와 라우팅을 구성하고 본사·지사 구간의 기본 연결성을 확인했습니다.

  3. 03
    ACL 구현·반복 검증

    본사·지사·재택근무의 접근 기준을 장비 정책으로 변환하고 허용·차단 시나리오를 반복 테스트했습니다.

  4. 04
    VPN·Dynamic NAT 협업

    팀원과 함께 구성을 완성했습니다. 제 단독 기여로 강조하기보다 전체 네트워크 완성을 위한 협업 항목으로 구분했습니다.

  5. 05
    통신 검증·최종 보고

    전체 구성 완료 후 본사·지사 네트워크 시연 영상을 직접 제작하고, 테스트 결과를 최종보고서에 정리했습니다.

가장 애먹었던 부분은 ACL이었습니다. 규칙 하나가 틀리거나 순서가 맞지 않으면 원래 되어야 할 통신까지 한꺼번에 막혔습니다. 그래서 본사와 지사의 허용 기준을 따로 적어 두고, 출발지와 목적지, 서비스 종류를 하나씩 바꿔 가며 확인했습니다.

06 / TROUBLESHOOTING

ACL에서 막힌 부분을 확인한 방법

처음에는 통신이 안 될 때마다 ACL부터 고쳤는데, 오히려 원인을 찾기가 더 어려워졌습니다. 이후에는 ACL을 제외한 상태에서 라우팅이 되는지 먼저 확인했습니다. 기본 통신이 되면 ACL의 적용 인터페이스와 방향, 규칙 순서, IP 주소와 포트를 차례대로 봤습니다.

  • 필요한 서비스의 정상 연결 확인
  • 비인가 부서와 외부 접근 차단 확인
  • 본사·지사·재택근무 시나리오별 재시험
  • 성공과 실패 결과를 시연 영상으로 기록

07 / TEST SCENARIOS

ACL 기준표를 네 가지 통신 구간으로 나누어 검증했습니다.

처음에는 규칙을 한 번에 적용하려고 하면서 어느 조건에서 통신이 막히는지 찾기 어려웠습니다. 이후 본사 내부, 본사에서 지사, 지사에서 본사, 재택근무 구간으로 테스트 범위를 나누고 각 구간에서 출발지·목적지·서비스를 하나씩 바꾸어 결과를 확인했습니다.

01

본사 내부

일반 부서 간 Ping은 제한하고 보안팀은 관리 목적으로 전체 구간을 확인하도록 구성했습니다.

  • 전 부서 WEB·FTP·DNS 확인
  • DB는 개발·재무·보안만 허용
  • LOG는 개발·보안 중심으로 허용
02

본사 → 지사

업무 서버에 필요한 서비스만 허용하고 임의의 Ping과 불필요한 부서 간 통신은 차단했습니다.

  • 지사 WEB 접근 확인
  • 보안·서버 구간 FTP 확인
  • 인사·영업 동일 부서 예외 검증
03

지사 → 본사

지사 사용자는 본사 WEB·DNS를 사용하고 지사 서버는 로그 전송 경로만 추가로 허용했습니다.

  • 본사 WEB·DNS 접근 확인
  • 지사 서버 LOG 전송 확인
  • 그 외 본사 내부 접근 차단
04

재택근무

업무용 WEB·FTP 범위만 사용하도록 제한하고 내부망 Ping은 차단했습니다.

  • 본사 WEB·FTP 확인
  • 지사 WEB 접근 확인
  • 내부망 직접 Ping 차단

08 / ITERATION

설정을 바꾼 뒤에는 처음부터 다시 테스트했습니다.

ACL은 위에서부터 순서대로 적용됩니다. 앞쪽에 넓은 차단 규칙이 있으면 뒤에 허용 규칙을 넣어도 통신이 되지 않았습니다. 적용 방향을 반대로 넣어 같은 문제가 생긴 적도 있었습니다. 이후부터는 아래 순서를 정해 놓고 확인했습니다.

  1. 기본 연결성 확인ACL을 제외했을 때 라우팅과 인터페이스가 정상인지 확인
  2. 적용 위치 확인어느 인터페이스의 inbound/outbound에 적용되었는지 확인
  3. 규칙 순서 확인필요한 permit보다 넓은 deny가 먼저 평가되는지 점검
  4. 서비스 단위 확인Ping, WEB, FTP, DNS, DB, LOG를 개별 시험
  5. 반대 조건 확인허용 대상은 연결되고 비인가 대상은 실패하는지 함께 검증

ACL을 하기 전에는 명령어 형식만 맞으면 된다고 생각했습니다. 실제로 설정해 보니 먼저 누가 어느 서버의 어떤 서비스를 사용해야 하는지 정리해야 했습니다. 허용 테스트만 해서는 부족했고, 막혀야 하는 접근이 실제로 막히는지도 같이 봐야 했습니다.
