Eazy Hotel

보안 관제 구축 과정

웹 서비스에 취약점을 직접 만들어 재현하고, 조치 후 같은 공격이 차단되는지 확인했습니다. Ubuntu 서버 점검 스크립트의 공통 틀을 만들었고, cron 실행 결과를 터미널에 바로 보여주는 방식도 제안해 테스트했습니다.

01 / PROJECT

호텔 예약 서비스를 만들고
공격부터 관제까지 연결했습니다.

Eazy Hotel은 회원가입, 로그인, 객실 조회와 예약 기능이 있는 가상의 호텔 서비스입니다. 고객 정보와 예약 데이터를 다루고 외부 접속이 계속 발생하는 서비스라서, 웹 취약점과 네트워크 보안, 로그 관제를 한 프로젝트 안에서 시험하기에 적합하다고 판단했습니다.

계획서를 먼저 제출해 피드백을 받은 뒤 실제 환경을 만들었습니다. 외부망에서 들어오는 요청은 pfSense와 Suricata를 거쳐 DMZ의 웹 서버로 전달했고, 내부 업무망과 보안 관제망은 별도 구간으로 나눴습니다. 장비와 서버의 로그는 rsyslog, Graylog, GoAccess에서 확인하고 PMM으로 서버와 DB 상태를 확인했습니다.

저는 GNS3 네트워크 구성에 참여했고, 이후에는 취약점 재현과 조치 확인, 모의해킹 결과보고서 작성, 시스템 점검 스크립트 틀 작성에 더 집중했습니다.

모의해킹 결과보고서는 취약점 설명, 취약한 코드, 재현 절차, 공격 증거, 대응 방안, 수정 코드와 조치 후 결과 순서로 작성했습니다. 공격이 된다는 사실보다 왜 발생했고 어떤 코드를 바꾸면 막히는지를 남기는 데 집중했습니다.

진단 대상은 Eazy Hotel 웹 서비스였고, 인증·회원 관리·시스템 접근 영역에서 총 6개 항목을 정리했습니다.

05 / VULNERABILITIES

직접 재현하고 조치 결과를 확인한 취약점

01
SQL Injection

로그인 쿼리에 입력값이 직접 들어가도록 만들고, LIMIT 값을 바꿔 특정 계정으로 인증이 우회되는지 확인했습니다. Prepared Statement와 password_verify()를 다시 적용한 뒤 같은 입력이 막히는지 시험했습니다.

02
Open Redirection

로그인 후 이동할 next 값에 외부 주소를 넣어 다른 사이트로 이동하는지 확인했습니다. 내부 경로와 허용된 주소만 통과시키도록 검증 조건을 추가했습니다.

03
Session Fixation

로그인 전후에 PHPSESSID가 바뀌지 않는 상태를 재현했습니다. 로그인 성공 시 세션 ID를 새로 발급하도록 수정한 뒤 기존 ID가 더 이상 유효하지 않은지 확인했습니다.

04
Stored XSS

회원 정보에 저장한 스크립트가 예약 화면과 관리자 화면에서 실행되도록 취약한 출력 상태를 만들었습니다. htmlspecialchars()를 적용해 코드가 아닌 문자로 출력되는지 확인했습니다.

05
IDOR

예약 조회 조건에서 로그인 사용자의 member_id 확인을 제거했습니다. URL의 예약 번호만 바꿔 다른 사람의 예약을 조회·취소할 수 있는지 확인한 후 소유권 조건을 다시 넣었습니다.

06
SSRF

partner-url 값을 검증하지 않고 서버가 요청하게 만든 뒤 file://와 내부 주소 접근을 시험했습니다. 허용 프로토콜과 도메인을 제한하고 내부망 주소는 차단했습니다.

06 / SYSTEM CHECK

67개 점검 항목의 공통 틀을 만들었습니다.

시스템 점검은 KISA 주요정보통신기반시설 취약점 분석·평가 가이드를 참고했습니다. 멘토님 피드백을 받은 뒤, 팀원들이 항목별 함수를 나누어 작성하기 전에 결과 형식과 집계 방식부터 맞출 필요가 있다고 생각했습니다.

제가 먼저 만든 초기 틀

AI를 활용해 초안을 만들고, 실제 Ubuntu에서 67개 점검 결과가 나오는지 먼저 시험했습니다.

AI가 만든 내용을 그대로 사용한 것은 아닙니다. 점검 함수의 형태와 출력 구조를 빠르게 잡는 데 활용한 뒤, 실제 명령어와 파일 경로가 Ubuntu 환경에서 맞는지 하나씩 실행해 확인했습니다. wheel 그룹 대신 sudo 그룹을 확인하는 것처럼 실습 환경과 다른 부분도 직접 수정했습니다.

U-01부터 U-67까지 실행 결과와 양호·취약 개수가 한 번에 보이는 초기 형태를 만든 다음 팀원들에게 먼저 보여주며 “이런 방식으로 합치면 될 것 같다”고 공유했습니다. 이후 각자 작성한 점검 항목을 같은 형식에 넣을 수 있도록 공통 출력 함수와 실행 순서를 정리했습니다.

  1. result_print 함수항목 코드, 점검 내용, 양호·취약 결과와 필요한 조치사항을 같은 형식으로 출력
  2. 결과 자동 집계전체, 양호, 취약, 수동 확인 개수를 실행할 때마다 누적
  3. 실행 모드 분리전체를 보는 all 모드와 취약한 항목만 보는 vulnerable 모드 구성
  4. 67개 함수 순차 실행U_01부터 U_67까지 존재하는 함수를 찾아 순서대로 실행
  5. Ubuntu 환경 반영wheel 그룹 대신 sudo 그룹을 확인하는 등 실습 환경에 맞게 기준 조정

첫 점검에서는 root 원격 접속, 패스워드 복잡성, 계정 잠금, su 제한, 불필요 계정, 세션 종료, FTP root 차단, 로그인 경고문, 시스템 로깅까지 9개 항목이 취약으로 나왔습니다. 설정을 수정한 뒤 다시 실행해 67개 항목이 모두 양호로 표시되는 것을 확인했습니다.

07 / MY PROPOSAL

채택 여부와 별개로 직접 구현해 본 개선안

채택되지는 않았지만 직접 동작까지 확인한 제안

cron으로 정해진 시간에 점검 스크립트를 실행하고 결과를 로그 파일에 저장하는 내용이 있었습니다. 저는 여기에 결과를 현재 열려 있는 Ubuntu 터미널에도 바로 보여주면 관리자가 별도 명령어를 입력하지 않아도 확인하기 편하겠다고 생각했습니다.

실행 시간을 지정하고 활성 터미널(TTY)로 결과를 보내는 방법을 시험했습니다. 화면에 결과가 나타나는 것까지 확인해 영상으로 남겼지만, 팀의 최종 운영 방식으로는 채택되지 않았습니다. 실제 적용 성과처럼 쓰지 않고 제가 냈던 개선 의견과 테스트 기록으로 남깁니다.

CRON · TTY OUTPUT TEST

점검 결과 실시간 출력 테스트

예약한 시간에 스크립트가 실행되고, 열려 있는 Ubuntu 터미널에 점검 결과가 표시되는지 확인했습니다.

08 / DOCUMENTATION

점검 결과는 조치 전후가 보이도록 정리했습니다.

시스템 점검보고서에는 총 67개 항목 중 취약했던 9개 항목과 실제 설정 변경 내용을 기록했습니다. 단순히 최종 결과만 쓰지 않고 수정한 파일과 설정값, 서비스 재시작 명령, 재점검 결과를 함께 남겼습니다.

cron 자동 실행과 날짜별 로그 저장 방식도 보고서에 포함했지만, 앞에서 소개한 터미널 실시간 출력은 별도로 제안하고 시험한 방식입니다.
